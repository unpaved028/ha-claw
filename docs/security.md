## The core problem

A language model decides which service to call. Models are steerable by whatever text ends
up in their context — including entity names and automation aliases coming from your own
Home Assistant. So the design does not try to make the model trustworthy. It puts a
deterministic check between the model's decision and the actual service call.

Two layers do the work:

1. **An allowlist**, enforced in code, that decides which service calls can happen without
   asking. It cannot be talked around, because the model's output is data to it, not
   instruction.
2. **A confirmation gate** for everything else, bound to the human who triggered it.

Everything below is implementation detail of those two ideas.

## Domain allowlist

`ha_call_service` accepts only these domains — the `SAFE_DOMAINS` set in
[`src/tools/ha-tools.ts`](../ha-claw/src/tools/ha-tools.ts):

```text
light          switch         media_player   fan
climate        cover          vacuum         humidifier
water_heater   scene          number         select
input_boolean  input_number   input_select   input_text
```

Anything else is rejected with an error pointing the model at
`ha_call_service_dangerous`, which requires confirmation.

Two domains are **guarded**: `lock` and `alarm_control_panel`. They must never be reached
without confirmation, including indirectly.

`script` and `button` are deliberately *not* on the safe list. Their effect cannot be
inspected before running them, and until v0.9.2 `script.turn_on` on a door script was a
one-call bypass of the entire lock protection.

### Cover exception

Before any `cover` service call, each target entity's `device_class` is checked. These are
rejected and routed to the confirmation path:

```text
garage   gate   door
```

`shutter`, `blind`, `curtain` and `awning` stay on the everyday path. Opening a blind is not
the same act as opening a garage.

### Scene exception

Before any `scene` service call, the scene's `attributes.entity_id` list is inspected. If any
member belongs to a guarded domain, the call is rejected. A scene named "Good night" that
also unlocks the front door goes through the gate.

## Entity and domain validation

Every `entity_id` must start with `<requested domain>.`. A request with
`domain: "light"` and `entity_id: "lock.front_door"` is rejected, even though the domain
check on its own would have passed.

The order of construction matters too. Until v0.9.2 the model-supplied `data` object was
spread into the service payload *after* `entity_id`, so `data: { entity_id: "lock.x" }`
silently replaced the target that had just been validated. The spread order is now reversed
and the prefix check applies to every entity in the batch. The same validation runs in
`ha_call_service_dangerous` and `ha_light_set_scene`.

## The confirmation gate

Any tool registered with `dangerous: true` suspends the agentic loop until the user answers.
The eight dangerous tools are listed in [tools.md](tools.md#danger-flag-and-complexity).

| | Telegram | Web UI |
| --- | --- | --- |
| Prompt | Inline keyboard, yes/no | Modal with the tool name and arguments |
| Bound to | The user ID that triggered it | The browser session |
| Timeout | 60 s → denied | 60 s → denied |
| Concurrency | Per callback ID | Queue; two dialogs for two actions |

The gate shows the tool name and its arguments, not a natural-language paraphrase, because a
paraphrase is generated by the same model whose decision you are being asked to check.

Two failure modes that were fixed and are worth not regressing:

- **The Web UI held a single confirmation slot.** A second dangerous action overwrote the
  first, whose timeout guard then no longer recognised itself. The promise never resolved,
  the loop stalled and the HTTP request hung open. It is a `Map` now.
- **Telegram confirmations were not bound to a user.** In a group chat any whitelisted member
  could approve someone else's dangerous action. The triggering `userId` and `chatId` are now
  stored with the confirmation and compared in the callback handler. The same applies to the
  fast-track buttons on proactive task notifications.

## Telegram access control

The bot answers nobody who is not in `telegram_allowed_user_ids`. The whitelist guard is
middleware, registered before every handler, and it drops non-whitelisted messages silently
rather than replying — an error reply confirms the bot exists.

Startup fails if a bot token is configured without any allowed user IDs. There is no
"allow everyone" mode.

Whitelisted users are **trusted operators**. There are no per-user permissions: anyone on the
list can do anything, including approving their own dangerous actions and running the backlog
processor. Put the bot in a private chat unless you want everyone in a group to have that.

## What leaves your network

This is the honest version. HA-Claw is not local inference.

**Sent to your LLM provider through OpenRouter, on every request:**

- Your message.
- The system prompt, which contains the personality profile and a **compressed entity cache**:
  floor names, area names, friendly names and entity IDs of controllable entities plus
  window, door, motion, smoke and moisture sensors, with their current states.
- Relevant memory cards, learned corrections, active prompt patches, usage patterns and
  recent error context.
- Tool results — including entity states, automation configurations and script sequences the
  agent read while answering.
- Conversation history, pruned to a token budget.

**Sent to OpenAI, only if you configured `openai_api_key`:** the audio of Telegram voice
messages, for Whisper transcription. This does not route through OpenRouter.

**Sent to Telegram, only if you configured a bot:** the conversation, as Telegram messages.

**Stays local:** every service call, all storage, the scheduler, system health checks, the
action log. The reasoning is remote; the acting is local.

If model-side data processing is unacceptable for your household, no configuration option
fixes that — the architecture is wrong for you.

## Secret handling

- The Pino logger redacts recognised secret patterns (API keys, bearer tokens) before
  writing.
- `openrouter_api_key` and `openai_api_key` are never returned by `GET /api/settings`.
- `dev-options.json` holds real keys in development and is gitignored. `.env` files are too.
- The Supervisor token is read from the environment and never persisted.

Redaction is pattern-based, so it is best-effort. Check before pasting a `debug` log into an
issue.

## Network exposure

`config.yaml` sets `ingress: true` and publishes no ports. The Web UI is reachable only
through Home Assistant, which authenticates the user first. There is no login screen in
HA-Claw because there is no unauthenticated path to it.

The server binds `0.0.0.0` inside the container (`127.0.0.1` in standalone mode). In add-on
mode it also rejects the connection unless the peer is the Ingress gateway `172.30.32.2`,
loopback (Docker `HEALTHCHECK`), or the hassio network `172.30.32.0/23` (Supervisor
watchdog). Publishing the port is no longer enough to reach the API. The check uses the
socket address, not `X-Forwarded-For`.

The add-on requests `hassio_role: backup`, which is the least privileged role that can read
`GET /backups/info` for the backup age check.

## Prompt injection

Text from your Home Assistant enters the model's context: entity names, area names,
automation aliases, sensor attributes. An attacker who can write those strings — a
compromised integration, a malicious Zigbee device name, a shared automation blueprint — can
put instructions in front of the model.

What that buys them, and what it does not:

- **They can change what the agent says.** Nothing prevents injected text from steering the
  wording of a reply.
- **They can make the agent attempt an action.** The model can be talked into calling any
  tool.
- **They cannot execute a guarded action.** The allowlist is code, not prompt. An injected
  instruction to unlock the front door still lands in the confirmation gate, which shows you
  the real tool name and the real entity ID.

So the mitigation is the human in the loop, which is exactly why the gate displays raw
arguments rather than a model-written summary. Read the entity ID before you tap yes.

## Audit trail

Every Home Assistant service call is appended to `store/actions.jsonl` with its arguments,
result and — where one can be computed — the inverse call needed to undo it. Visible under
**Status → Actions**, with a rollback button per entry. Retained for 7 days.

After anything unexpected, that log is the record of what actually happened, independent of
what the agent said it did.

## Known limitations

Stated plainly, because a security document that only lists strengths is marketing:

1. **The safety-policy tests do not talk to Home Assistant.** Cover `device_class` and scene
   members are injected as fixtures. A live entity whose class is missing still falls
   through to the everyday path, same as before.
2. **Tool-argument validation is the subset the registry actually writes** (`type`,
   `required`, `properties`, `anyOf`, `items`). It is not a full JSON Schema implementation.
3. **The AppArmor profile is broad** (`file,` and `network,`) so Node can start. It still
   earns the add-on the custom-profile security point; it is not a tight jail.
4. **Approved backlog tasks execute with the full tool set.** Approving a task is a broader
   grant than approving a single action. Read the proposed solution before approving it.
